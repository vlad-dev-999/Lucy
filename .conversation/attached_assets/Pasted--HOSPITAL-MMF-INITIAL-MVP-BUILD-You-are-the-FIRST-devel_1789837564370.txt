# HOSPITAL MMF — INITIAL MVP BUILD

You are the FIRST development instance for a new Hospital MMF application.

We are intentionally starting from scratch.

The actual legacy Excel workbook is the foundation of this project.

Your job is to build the first working MVP in a structured sequence AND leave the repository with versioned project-state documentation so that the NEXT Replit instance can continue development without relying on this conversation.

Do not assume any previous Replit implementation exists.

Inspect the actual workbook first.

============================================================
1. WHAT WE ARE BUILDING
============================================================

The hospital has an existing internal Tools Committee system.

That system maintains the hospital's item vocabulary and produces the hospital's MMF Excel export.

MMF means:

MONTHLY MAINTENANCE FIGURE

It represents the expected monthly requirement/consumption of an item.

The existing internal system is confined to the hospital's internal network.

Doctors and authorised users from multiple departments need a secure external collaboration environment to establish the next year's MMF.

Therefore this application is NOT a replacement for the internal Tools Committee system.

It is a secure external:

CURATION
+
COLLABORATION
+
GOVERNANCE
+
FORECASTING

layer around the existing system.

The eventual product flow is:

LEGACY EXCEL

4. KNOWN WORKBOOK CHARACTERISTICS
============================================================

The legacy workbook contains data-quality issues that the application must be capable of detecting and presenting for human review.

There are approximately:

6,195 unique PVMS/NIV identifier values

against approximately:

6,204 records.

Examples of nomenclature variations include:

NIV/6344

"Tab Letemovir 240 mg"

vs.

"Tab Letermovir 240 mg"


NIV/6086

"Papain Urea ointment 15 gm"

vs.

"Papain urea ointment 15gm"


LAB/GEN/HIST/66

"Primary Antibody ... CD 30"

vs.

"Primary Antibody ... CD-30"

There are also serious identifier conflicts.

For example:

NIV/22

appears against unrelated descriptions including:

"Graduated compression stockings"

and

"Guardian Sensor (Medtronic)"

Another identifier appears against different pedicle-screw descriptions.

These are examples of why identifier matching cannot be treated as proof of clinical equivalence.

The system must detect such conditions.

It must NEVER silently merge them.

These examples are development clues, not hard-coded assumptions about future datasets.

Always inspect and validate the actual workbook.

============================================================
5. PVMS / NIV / CANONICAL ITEM ID
============================================================

PVMS and NIV are ITEM IDENTIFIERS.

They are NOT budget heads.

An item may have:

- PVMS
- NIV
- both
- neither

Some legacy records legitimately have neither.

Therefore:

BLANK PVMS/NIV = REVIEW WARNING

It is not automatically an import error.

Every item must receive an internal immutable:

CANONICAL ITEM ID

Example:

CAN-000001

The Canonical Item ID is independent of PVMS/NIV.

Never use PVMS or NIV as the database primary key.

============================================================
6. BUDGET HEADS
============================================================

There are exactly TWO budget heads:

DGLP
ECHS

PVMS and NIV are not budget heads.

An item may have separate MMF quantities for DGLP and ECHS.

Example:

Item:
Ceftriaxone 1 g

DGLP MMF = 100
ECHS MMF = 25

Never collapse these into one value.

The application must preserve them separately throughout:

- import
- editing
- forecasting
- approval
- release
- export

============================================================
7. PRODUCT PRINCIPLES
============================================================

This is a governed data product, not a spreadsheet editor.

Non-negotiable principles:

1. Never destroy source data.
2. Never silently merge vocabulary.
3. Never silently delete vocabulary.
4. Human users decide clinical equivalence.
5. Automation detects candidates and anomalies.
6. Legacy vocabulary and canonical vocabulary are separate.
7. Canonical Item ID is independent of PVMS/NIV.
8. Historical revisions are immutable.
9. Every consequential action is auditable.
10. Department access is enforced server-side.
11. Benchmark requirement is not actual expenditure.
12. Freeze is a governance state.
13. Frozen releases are immutable.
14. Post-freeze changes require controlled amendment.
15. Excel is a legacy interface, not the database model.

============================================================

============================================================
28. FREEZE
============================================================

Freeze is a core governance mechanism.

Example:

MMF 2027–28
Freeze:
15 February 2027 23:59

Before freeze:

- authorised users can edit
- departments review
- departments submit
- vocabulary review continues
- benchmark prices may update

At freeze:

Cycle transitions to FROZEN.

After freeze:

- ordinary MMF edits are rejected
- departmental submissions are read-only
- ordinary vocabulary changes are rejected
- frozen benchmark values cannot silently change
- dashboards remain available
- history remains available

Display prominently:

OPEN — X DAYS REMAINING

or:

FROZEN — RELEASE 1.0

Changes to freeze configuration must be audited.

============================================================
29. RELEASE
============================================================

A frozen cycle creates a reproducible release.

Example:

MMF 2027–28
Release 1.0
FROZEN

The release is immutable.

The final XLSX export is generated from this release, not mutable live data.
